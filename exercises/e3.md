# Exercise 3: Composing Concepts

## Exercise 3.1: Concepts for URL Shortening

**3.1.1 Contexts.** In `NonceGenerating`, contexts are for specifying scopes in which stored strings need to be unique. In the URL Shortening app, the context will end up being the `shortURLBase`, because we want to avoid conflicts where two shortlinks with the same `shortURLBase` also have the same `shortURLSuffix`.

**3.1.2 Storing used strings.**

a. `NonceGenerating` must store sets of used strings because it needs to ensure that, within any context, the same string is never used twice. Without some form of state like a set of used strings, we wouldn't know if a generated string was already in use.

b. In the given counter implementation, the set of used strings will be equal to the set of string representations of nonnegative integers less than the counter, i.e. assuming the counter starts at 0, and after some `generate`s ends up at n, the set of used strings will be {"0", "1", ..., str(n-1)}. This is because we can interpret the counter increment from n as the instruction to "register n, and move onto a new unused candidate string n+1".

**3.1.3 Words as nonces.**

a. One advantage of word-based nonces is that they are easy to communicate out loud, so a user creating the link can more easily share it to a large group of people without needing to read a complex code. One disadvantage of this scheme is that the set of common dictionary words may be smaller and more predictable than an alternative scheme, so a user creating a shortlink may end up with unwanted traffic to their target URL.

b. To add word-based nonces, I would modify the `NonceGenerating` action `generate` to take as input a `dictionary`, which is a set of strings that would act as the domain of allowed words. I would rewrite the action as follows:

generate (context: Context, dictionary: Set\<String\>) : returns (nonce: String) <br>
&emsp;**where** some string in the dictionary is not in the given context's used set<br>
&emsp;**then** add such a new string into this context's used set, and return that string

This would allow a URL Shortening app to enforce that every suffix is a common word.

## Exercise 3.2: Reactions for URL Shortening

**3.2.1 Partial matching.** The `generate` reaction only needs `shortUrlBase` because it is the only value needed to determine context in Nonce Generation (the `targetURL` is still passed, but as it is not needed, it is not bound to a name). The `register` reaction needs both arguments to register a short URL, so it names both.

**3.2.2 Omitting names.** This abbreviation isn't always done because it only applies when the variable name matches the argument name. In the cases of our `then` statements, most of them map variables to passed arguments under a different name (ex. `context: shortUrlBase` in reaction 1), so omitting either name (i.e. `context` or `shortUrlBase`) wouldn't express that mapping.

**3.2.3 Inclusion of request.** The first two reactions include `Requesting` because they are meant to connect a user's request for shortlink creation/registration to an application action, whereas setting expiry is not explicitly triggered by user request. 
A user explicitly requests a shortening, so then "generate" and "register" steps occur, but setting expiry will just happen in response to the registration step.

**3.2.4 Fixed domain.** For a fixed domain like "bit.ly", I would modify the `generate` and `register` reactions to use the hardcoded domain rather than naming one as an argument. I would rewrite the two as follows:

**reaction** generate <br>
**when** Requesting.shortenUrl () <br>
**then** NonceGenerating.generate (context: "bit.ly")

**reaction** register <br>
**when**<br>
&emsp;Requesting.shortenUrl (targetUrl) <br>
&emsp;NonceGenerating.generate (): (nonce) <br>
**then** UrlShortening.register (shortUrlSuffix: nonce, shortUrlBase: "bit.ly", targetUrl)

**3.2.5 Adding a reaction.** In order to respond to expiry, I would add a `deleteExpired` reaction which would do the following:

**reaction** deleteExpired <br>
**when** Expiring.expireResource () : (resource)<br>
**then** UrlShortening.delete (shortUrl: resource)

This would remove the shortlink from the URLShortening concept state when expiry occurs.

*Note:* in this case, Expiring [Resource] is parametrized where Resource is type String.

## Exercise 3.3: Extending the design

**3.3.1 Additional concepts.** I would design URL Shortening analytics with two additional concepts: `Counting` and `Ownership`. These would make it possible to collect analytics on an arbitrary resource, and for analytics to only be accessible to the owner user:

**concept** Counting [Resource] <br>
**purpose** track an event count for a resource, and make that count accessible to users <br>
**principle** an actor initializes a resource's counter; <br>
&emsp;the counter is incremented some number of times; <br>
&emsp;an actor can view the current total count on that resource<br>
**state**<br>
&emsp;a set of Resources with<br>
&emsp;&emsp;a count Number<br>
**actions**<br>
&emsp;initialize (resource: Resource) <br>
&emsp;&emsp;**where** the given resource is not in the set<br>
&emsp;&emsp;**then** add the given resource with a count of 0

&emsp;increment (resource: Resource)<br>
&emsp;&emsp;**where** the given resource exists in the set<br>
&emsp;&emsp;**then** increase that resource's count by 1

&emsp;view (resource: Resource) : returns (count: Number)<br>
&emsp;&emsp;**where** the given resource exists in the set<br>
&emsp;&emsp;**then** return that resource's count


**concept** Ownership [User, Resource] <br>
**purpose** provide a record of ownership of resources; limit access of resources from non-owners<br>
**principle** an actor can assign a resource to a user, and the user will function as the owner of the resource.<br>
**state**<br>
&emsp;a set of Resources with<br>
&emsp;&emsp;an owner User<br>
**actions**<br>
&emsp;assign (resource: Resource, user: User)<br>
&emsp;&emsp;**where** given resource is not in the set <br>
&emsp;&emsp;**then** adds resource to the set, with owner as the given user

*Note:* for the purpose of URL Shortening, both concepts are initialized with `Resource` equal to the String type.


**3.3.2 Three reactions.** For reactions which happen at creation, URL translation, and analytics inspection, I would create the reactions of `initialize`, `addView`, and `viewAnalytics` respectively, defined below:

**reaction** initialize<br>
**when** <br>
&emsp;Requesting.shortenUrl(user)<br>
&emsp;UrlShortening.register (): (shortUrl)<br>
**then**<br>
&emsp;Ownership.assign(resource: shortUrl, user)<br>
&emsp;Counting.initialize(resource: shortUrl)

**reaction** addView<br>
**when** UrlShortening.lookup(shortUrl)<br>
**then** Counting.increment(resource: shortUrl)

**reaction** viewAnalytics<br>
**when** Requesting.viewAnalytics(user, shortUrl)<br>
**where** in Ownership concept, the given user is the owner of shortUrl<br>
**then** Counting.view(resource: shortUrl)<br>

**3.3.3 Feature requests.** I would address each feature request as follows:
1. **Users choose own short URLs.** We could implement this by modifying the `generate` reaction to respond to requests of the form `Requesting.shortenUrl(targetUrl, shortUrlBase, shortUrlSuffix)` (i.e. `shortUrlSuffix` is optional) by directly triggering `UrlShortening.register` with no nonce creation, and with the precondition that the `shortUrlSuffix` isn't already in use under the `shortUrlBase`. The Counting and Ownership concepts/reactions still function the same, and in the case when `shortUrlSuffix` isn't provided, it uses the existing functionality.
2. **Word-as-nonce.** As in 3.1.3, we could modify the `NonceGenerating.generate` action to accept a `dictionary` (set of String words). Then, the `generate` reaction from 3.2 can additionally pass the desired dictionary as an argument to `NonceGenerating.generate` when it invokes the action.
3. **Grouped analytics.** We can first add an action to `Counting` which performs group analytics, i.e. it returns the sum of counts for a given set of resources. Then, a new reaction similar to `viewAnalytics` can query Ownership and UrlShortening to get the requester’s short URLs sharing a target, and trigger the new `Counting` group action to return the grouped analytics owned by that owner. <br> *Note:* I think this feature request is only a good addition if it is intended to show the analytics across only a given owner's shortlinks to a targetUrl. Otherwise, an owner could potentially see analytics from other shortlinks directing to one of their target URLs, which is a privacy issue.
4. **Not-easily-guessed URLs.** We can modify the logic of `NonceGenerating.generate` to randomly generate longer/more complex URL suffixes that are unpredictable, while still maintaining that strings are unique per-Context. This would be better than, for instance, a counter-based approach where suffixes are very predictable.
5. **Analytics to non-users.** We could extend the `initialize` reaction and `Ownership` concept so that when `UrlShortening.register` occurs, a "secret key" string is also generated within `Ownership` (via some new action which creates and returns it to the user) that can function as proof of ownership for a given Resource. Then, another reaction similar to `viewAnalytics` can be written to return analytics on a shortUrl when the correct secret key is supplied. <br> *Note:* though it is convenient, I would advise against adding this feature, because removing the need for any user registration/established credentials would make the system more prone to undesired access (i.e. anyone with the secret key would gain access).
