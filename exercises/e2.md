# Exercise 2: Understanding Concepts

## Exercise 2.1: Reading a concept

**2.1.1: Invariants.** One intended invariant of the state is that a registry holds at most one request per item (this request holds the associated count for the item). Another intended invariant is that every item is purchased at most as many times as its count, i.e. its purchase counts do not exceed its request counts. I think the second invariant is more important, because if broken, it would violate the purpose and the user would receive an item they don't want (or more units than they wanted). The action most affected by this invariant is `purchase`, and it maintains this by requiring that the request count is at least the proposed purchase count plus the sum of the counts of all existing purchases.

**2.1.2 Fixing an action.** The `removeItem` action fails to preserve the second invariant described above, and it can be broken with the following set of actions:
```
reg = create(Alice);
addItem(reg, Hat, 1); // request one hat
open(reg);
purchase(Bob, reg, Hat, 1);
removeItem(reg, Hat);
```
In this case, one `Hat` has been purchased for `reg`, but a request no longer exists for it, so the request count is effectively 0. One possible way to fix this is by only allowing `removeItem` to remove the request if the passed item has no purchases.

**2.1.3 Inferring behavior.** A registry can be opened and closed repeatedly, as the `open` action only requires that the registry exists and is inactive, while `close` only requires that it exists and is active. One possible reason to allow this is for users who want to reuse a registry for multiple occasions; for instance, someone may want to open the registry for the holidays, close it after, then reopen it later for their birthday.

**2.1.4 Registry deletion.** A registry deletion action would be useful in the cases that someone accidentally creates a registry, or the registry was made for an event that was later cancelled. A few reasons against it could be that the `close` action already serves a similar purpose by disabling future purchases until reopened, and that registry deletion could erase useful historical information (e.g. purchase history might also be deleted, or a purchase may be left associated with a registry that no longer exists).

**2.1.5 Queries.** A registry owner would likely want to make the query for all Purchases associated with Requests on their registry, where they would look at the items, purchasers, and purchase counts. A gift giver might frequently want to query for the set of Requests on a given active registry, alongside their preexisting Purchases to identify what is still available for purchase.

**2.1.6 Hiding purchases.** I would augment the concept specification by adding a `hidePurchases: boolean` flag to each registry's state, and the registry owner's queries for Requests would respect the flag by not returning the set of Purchases when `hidePurchases` is true. Additionally, I would add a `setHidePurchases` action specified by:
    
setHidePurchases(registry: Registry, hide: boolean) 
<br>&emsp;**where** registry exists
<br>&emsp;**then** set `hidePurchases` for the given registry to the value of hide, i.e. hide purchases from the recipient if hide is true.

This would allow the owner to decide whether they want to see the list of purchases, and for the system to remember the user's preference by keeping it in state.

**2.1.7 External types.** Using an external Item/User type like an Item SKU code is preferred because other information about Items or Users may be subject to change, and the system should rely on a stable identifier for each of its records. For instance, using an Item name or price would not be reliable because a name might later be shortened for readability or price might increase due to production costs, and this would require the system to identify and correct all references to that Item as a result. Similarly, multiple Users might share the same name (First + Last), so records across two different users may get confused. For stability, it is better to reference an external entry that uniquely identifies the record.

## Exercise 2.2: Extending a familiar concept

**2.2.1 Concept state.** I would use the following state:

**state**
<br>&emsp;a set of Users with
<br>&emsp;&emsp;a username String
<br>&emsp;&emsp;a password String

**2.2.2 Concept actions.** I would specify `register` and `authenticate` as:

register (username: String, password: String) : return (user: User)
<br>&emsp;**where** no User exists with the given username
<br>&emsp;**then** create a new User with the given username and password, and return it

authenticate (username: String, password: String) : return (user: User)
<br>&emsp;**where** a User exists with the given username and password
<br>&emsp;**then** return that User

**2.2.3 Invariant.** An essential invariant is that no two registered Users have the same username. The `register` action maintains this by requiring that the newly registering user does not have the same username as any existing User. The `authenticate` action also preserves this, as it doesn't modify state.

**2.2.4 Email confirmation extension.** I would first expand registration to require email for every User, and the state would store this email as well as confirmation details. I would make the following modifications to the state and `register` action:

**state**
<br>&emsp;a set of Users with
<br>&emsp;&emsp;a username String
<br>&emsp;&emsp;a password String
<br>&emsp;&emsp;*an email String*
<br>&emsp;&emsp;*a confirmed Boolean*
<br>&emsp;&emsp;*a confirmationToken String*

register (username: String, password: String, *email: String*) : return (user: User, *token: String*)
<br>&emsp;**where** no User exists with the given username
<br>&emsp;**then** *generate a new unique secret token that is not associated with any existing user*. Then create a new User with the given username, password, *email, token, and the confirmed flag set to false*, and return the User *and token*.

Then for the new `confirm` action:

confirm(token: String) : return (user: User)
<br>&emsp;**where** there exists an unconfirmed User whose confirmationToken is equal to the given token
<br>&emsp;**then** set that User's confirmed flag to true, and return the User.

Additionally, `authenticate` will need to be modified to ensure the user is confirmed:

authenticate (username: String, password: String) : return (user: User)
<br>&emsp;**where** a *confirmed* User exists with the given username and password
<br>&emsp;**then** return that User

## Exercise 2.3: Comparing concepts

I would specify the `PersonalAccessTokening` concept in the following way:

**concept** PersonalAccessTokening [User, Scope] <br>
**purpose** allow for limited and revocable access to a user’s account, without using its password <br>
**principle** 
<br>&emsp;a user creates a token, and selects its scopes and expiration; 
<br>&emsp;the user provides the token to a client, such as a command-line tool or GitHub API client;
<br>&emsp;the client is able to take actions within the user's account as specified by the permission scopes;
<br>&emsp;finally, the token expires or the user deletes the token, after which the client can no longer use it to take actions.<br>
**state**
<br>&emsp;a set of Tokens with
<br>&emsp;&emsp;an owner User
<br>&emsp;&emsp;a secret String
<br>&emsp;&emsp;a set of scopes Set\<Scope\>
<br>&emsp;&emsp;an expiration Optional\<DateTime\><br>
**actions**
<br>&emsp;create(owner: User, scopes: Set\<Scope\>, expiration: Optional\<DateTime\>) : return (token: Token, secret: String) 
<br>&emsp;&emsp;**then** generate a new unique secret (not shared by any existing token). Then create a Token with this owner, secret, scopes, and expiration, and return the Token and secret.

&emsp;authenticate(secret: String, requiredScopes: Set\<Scope\>) : return (user: User) 
<br>&emsp;&emsp;**where** an unexpired token exists with the given secret, requiredScopes is a subset of that token's scopes,
<br>&emsp;&emsp;**then** return the owner User of that token.

&emsp;delete(owner: User, token: Token)
<br>&emsp;&emsp;**where** the given token exists, and the given owner owns that token
<br>&emsp;&emsp;**then** delete the given token.

**Note:** `PersonalAccessTokening` is different from `PasswordAuthenticating` because it is intended to be a voidable and restricted method of authenticating, which is secondary to the persistent method of authenticating via password. This purpose is enabled by the inclusion of an expiration time, scope restriction, and option to delete the token, so clients using the token can only take certain actions and only while the token is valid. I think GitHub could make this purpose clearer by referencing this distinction at the top of the page. Right before the first description sentence, I think they could add that "A personal access token is designed to be a scoped and revocable method of authenticating," which would clarify how its purpose is different to that of a password.

## Exercise 2.4: Defining familiar Concepts

### 2.4.1: URL Shortening Concept

**concept** URLShortening [URL] <br>
**purpose** provide a short URL suffix that redirects to a longer URL, to make it easier to navigate to the page <br>
**principle**
<br>&emsp;a user provides a full URL, and optionally requests a unique particular suffix;
<br>&emsp;the suffix is associated with the full URL and used to form a shortened URL;
<br>&emsp;any user navigates to the shortened URL, and the page resolves to the associated full URL <br>
**state**
<br>&emsp;a set of URLMaps with
<br>&emsp;&emsp;a suffix String
<br>&emsp;&emsp;a fullURL URL<br>
**actions**
<br>&emsp;create(fullURL: URL, suffix: Optional\<String\>) : return (chosenSuffix: String)
<br>&emsp;&emsp;**where** suffix is absent, or no URLMap exists with the given suffix as its suffix
<br>&emsp;&emsp;**then** if suffix is not provided, generate a suffix that is not used by any existing URLMap;
<br>&emsp;&emsp;&emsp;create a new URLMap with the suffix (provided or generated) and fullURL;
<br>&emsp;&emsp;&emsp;then return the chosen suffix
<br>&emsp;resolve(suffix: String) : return (fullURL: URL)
<br>&emsp;&emsp;**where** a URLMap exists with the provided suffix
<br>&emsp;&emsp;**then** return the fullURL associated with that URLMap

**Note:** I chose not to construct or specify a full shortened URL in this concept, as I think that could involve a separate `URLConstructor`-like concept which is aware of external details like a base URL. The primary focus of this concept is creating the suffix which maps to the full URL.

### 2.4.2 Shopping Cart Concept

**concept** ShoppingCart [User, Item] <br>
**purpose** allow a user to consolidate the items they would like to order<br>
**principle**
<br>&emsp;a user creates a shopping cart;
<br>&emsp;the user adds items they would like to order into the cart, with their respective quantities;
<br>&emsp;finally, the user checks out the cart when they want to place an order<br>
**state**
<br>&emsp;a set of Carts with
<br>&emsp;&emsp;an owner User
<br>&emsp;&emsp;a set of Entries
<br>&emsp;a set of Entries with
<br>&emsp;&emsp;an item Item
<br>&emsp;&emsp;a count Number<br>
**actions**
<br>&emsp;create(owner: User): return(cart: Cart)
<br>&emsp;&emsp;**then** create a Cart with the given owner and an empty set of entries (i.e. the cart is empty), and return it
<br>&emsp;add(cart: Cart, item: Item, count: Number)
<br>&emsp;&emsp;**where** count is a positive integer
<br>&emsp;&emsp;**then** if an Entry for the given item already exists in the given Cart, add count to that Entry's count; else create a new Entry with the given item and count, and add it to the Cart's set of entries.
<br>&emsp;remove(cart: Cart, item: Item, count: Number)
<br>&emsp;&emsp;**where** count is a positive integer, and the given Cart contains an Entry with the given item and count at least as large as the given count
<br>&emsp;&emsp;**then** if the given count equals that Entry's count, remove that Entry from the Cart and delete the Entry; else subtract count from the Entry's count
<br>&emsp;checkout(cart: Cart)
<br>&emsp;&emsp;**where** the given Cart contains at least one Entry
<br>&emsp;&emsp;**then** delete all of the Cart's Entries, and delete the Cart

**Note:** I wrote `checkout` to only delete parts of the state, as I think order creation should be a separate concept that can maintain its own state/object creations when `checkout` is called.

### 2.4.3 Time-Based One-Time Password (TOTP) Concept

**concept** TOTPAuthenticating [User, Device] <br>
**purpose** make user authentication more secure by requiring a time-sensitive code; prevent account access using a stolen password alone <br>
**principle**
<br>&emsp;a user enrolls a device in TOTP authentication, which generates a shared secret stored on both the server and the user's machine;
<br>&emsp;the user goes to authenticate, and their TOTP client provides them a time-sensitive code;
<br>&emsp;the user enters the code within the timeframe, the server independently calculates a code, and the user is authenticated if the two codes match<br>
**state** <br>
*on server:*
<br>&emsp;a set of TOTPAccounts with
<br>&emsp;&emsp;a user User
<br>&emsp;&emsp;a secret String <br>
*on each Device:*
<br>&emsp;a set of TOTPEntries with
<br>&emsp;&emsp;a user User
<br>&emsp;&emsp;a secret String <br>
**actions**
<br>&emsp;enroll(user: User, device: Device)
<br>&emsp;&emsp;**where** no TOTPAccount has user equal to the given user
<br>&emsp;&emsp;**then** generate a new secret string, create a TOTPAccount on the server with the given user and generated secret, and create a TOTPEntry on the user's Device with the same user and same secret
<br>&emsp;generate(user: User, device: Device) : return (code: String)
<br>&emsp;&emsp;**where** a TOTPEntry exists on the given Device for the given user
<br>&emsp;&emsp;**then** compute a code from a cryptographic function that takes as input that TOTPEntry's secret, and the current timestep, and return that code.
<br>&emsp;authenticate(user: User, code: String) : return (user: User)
<br>&emsp;&emsp;**where** a TOTPAccount exists for the provided user, and the same cryptographic function computed on that account's secret and the current timestep returns code equal to the supplied code
<br>&emsp;&emsp;**then** return the provided user

**Note:** I chose to make the `authenticate` action return back the user it receives as an argument, as `authenticate` should not change state within the TOTP system at all. To implement something like MFA, a wrapper concept can identify that the returned user means TOTP succeeded, and it should maintain its own state of whether full authentication is complete for the user.
